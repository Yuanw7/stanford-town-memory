# 从一段对话理解小镇 Memory：架构、操作与排错

更新日期：2026-10-18。本文供理解与学习，基于本项目当前实现和实验，不涉及新的框架选型或云服务报价。第 12 节补充情景聊天网站的公开机制及对本项目的启发。

建议按顺序阅读：先看第 1～4 节理解系统怎样工作，再看第 5～7 节理解方案与成本，最后按第 8～10 节操作和排错。教学示例不等于真实实验输入；标为“建议”的设计尚未完整实现。

## 1. 先回答：我们现在到底用了什么 Memory 架构？

**当前采用“外部持久化记忆 + 检索后装入上下文”的基本架构，并在这个架构下比较不同的写入和检索策略。**

可以把它理解成开卷考试：数据库是书架，检索程序负责找页码，上下文是考场桌面，生成模型负责阅读和回答。书架能放很多书，桌面只能摆下少数几页。

普通的一次模型请求不会把小镇对话自动写进模型权重。我们的“长期记忆”由程序保存，下次调用前再取出相关内容。Ollama 负责推理，应用程序负责决定保存和传入什么。

### 1.1 三个容易混淆的词

| 名称 | 是什么 | 例子 |
| --- | --- | --- |
| Agent memory | 角色经历、事实和任务等信息，以及管理它们的机制 | 小林记得答应给小陈送书 |
| Context，上下文 | 本次实际交给模型的输入材料；窗口还要给输出留空间 | 身份、问题、近期对话、选中的送书记录 |
| RAM / KV cache | 运行模型和处理请求的计算资源 | Mac 统一内存、推理缓存 |

把历史从上下文移到外部存储，可以减少本次输入；它不等于模型权重变小，也不等于系统 RAM 按相同比例下降。KV cache 是计算缓存，不能代替跨请求可检索的角色记忆库。

### 1.2 项目中有两条实现路径

| 路径 | 实际使用什么 | 已验证到哪里 |
| --- | --- | --- |
| 在线小镇 | AI Town 引擎 + 自托管 Convex 的数据/向量能力 + Ollama | 已运行角色互动和持久化验证；新策略尚未完整替换在线记忆流程 |
| 离线研究 | Node.js 策略类 + 本地事务存储/JSON 快照 + 本地精确余弦检索 + Ollama | 已比较 baseline、预算检索、分层原型和原文归档策略 |

因此，“已经写了归档策略”不表示地图上的所有角色都已经在使用它。本地 JSON 快照也不能称为已部署的独立向量数据库。当前小规模策略比较直接遍历本地向量计算相似度，尚未验证与 Convex 候选检索完全等价。

### 1.3 四种策略分别放在哪里

| 策略 | 保存的主要内容 | 怎样检索 | 代码入口 |
| --- | --- | --- | --- |
| baseline | 会话摘要、重要性、满足条件时生成的反思及向量 | 相似度候选结合时间/重要性等评分，选 Top-K | [baseline-policy.js](../lib/baseline-policy.js) |
| budgeted_retrieval | 可沿用基线的记忆 | 选取时增加精确 token 预算，超限整条跳过 | [memory-retrieval.js](../lib/memory-retrieval.js) |
| archive_retrieval | 逐消息原文、作者、UTC 时间、来源、向量 | 当前按观察时间过滤，再用余弦排序和预算选择 | [archive-policy.js](../lib/archive-policy.js) |
| tiered_memory | 原文、版本化事实、明确接受的承诺及执行回执 | 按查询意图/时间取候选，再按预算选择 | [tiered-policy.js](../lib/tiered-policy.js)、[tiered-store.js](../lib/tiered-store.js) |

“分层”是按信息职责组织数据，不是每层必须启动一套数据库。当前有部分层次的原型，通用原文回查、长期整理和完整在线任务链仍待补齐。

## 2. 用一段对话走完一次记忆操作

以下是教学示例，人物和消息用于解释机制；时间按 UTC 写明，避免机器时区改变含义：

```text
2026-11-01 09:00 UTC，小陈：请你在今天 12:00 UTC 前把蓝色书送给我。
2026-11-01 09:01 UTC，小林：我答应在今天 12:00 UTC 前把蓝色书送给你。
```

稍后问小林：“你今天中午前答应做什么？”下面以当前归档策略解释程序的操作。

### 第一步：判断谁有资格记住

程序先检查这是哪个实验、哪个世界，以及谁参与了会话。小林和小陈可以保存自己可见的消息；没有听到对话的小王不能因为数据库里有记录就检索到。

作用域相当于档案柜上的锁：`experimentId + worldId + agentId`。它应进入检索、写入、缓存和去重键。先过滤权限再排名，不能先把别人秘密取出来，再提示模型“请忽略”。

### 第二步：保存原文和来源

归档方案按每个实际参与者保存可见会话，并为每条消息建立记录。下面是便于学习的记录形状，省略事务包装和部分真实字段，不是可直接导入的接口：

```json
{
  "scope": {"experimentId": "lesson", "worldId": "town-a", "agentId": "lin"},
  "record": {
    "id": "archive:message-2",
    "text": "2026-11-01T09:01:00.000Z 小林 (lin): 我答应在今天12:00 UTC前把蓝色书送给你。",
    "sourceEventIds": ["message-2"],
    "embedding": [0.12, -0.03, 0.08]
  }
}
```

示意向量只写了三个数字，当前实际向量为 1024 维。来源 ID 用于回到原始消息，核对作者和措辞。一次会话的全部记录校验成功后才提交，避免只保存一半；重复提交同一内容应跳过，相同 ID 却内容不同应报冲突。

### 第三步：把消息变成 Embedding

Embedding 是“用于比较含义的一串数字”，可以理解成图书分类坐标。当前由 `mxbai-embed-large` 生成，回答模型是 `town-qwen`；两者职责不同。

归档写入会调用向量模型，但不会为了这条消息再调用生成模型做摘要或事实抽取。向量不是压缩后可以直接读懂的原文，也不是事实真伪证明；原文仍需保留。

### 第四步：提问时找出候选

程序把问题也转成向量，与同一作用域内的记忆向量计算余弦相似度。含“送书、答应、截止时间”的消息可能排在前面。

这类流程通常称为 RAG，即“先检索材料，再让模型根据材料回答”。Agent memory 还需要在它之外处理写入、更新、时间和任务状态。

相似度只意味着内容相关，不意味着内容正确、最新或最重要。例如“我不答应送书”也可能与“答应送书”非常接近。

### 第五步：按预算组装上下文

归档实现默认最多选择三条，并同时检查 token 预算。Top-K 是“最多几条”，token 预算是“材料最多多长”，二者不能互相代替。

假设记忆预算为 512 token，程序测量完整展示文本，超限整条跳过，并记下原因。512 只是记忆部分，身份、问题、任务和模板也要占空间。

示意输入如下，实际模板以 runner 为准：

```text
身份：你是小林。
当前时间：2026-11-01 10:00 UTC。
可见记忆：
- 小陈请求今天12:00 UTC前收到蓝色书。
- 小林明确答应了这件事。
问题：你今天中午前答应做什么？
要求：依据提供的证据回答，证据不足时说明未知。
```

模型此时才读取这些文字并生成回答。数据库里没有被选中的历史不会自动进入它的视野。

### 第六步：区分“回答得对”和“真的做完”

回答“我要送书”证明理解了任务。只有执行器检查库存、接收人和截止时间，实际投递并生成回执，才能证明完成。

当前归档策略没有内置持续任务状态和关键承诺固定保留。项目已有单步合成投递执行器，分层原型也有承诺/回执机制；这些不等于在线小镇已实现自主接受、取消、重规划的完整任务链。

## 3. 如果换一种记忆架构，这段对话会怎么处理？

### 方案 A：每次带上全部历史

操作：保存原文，每次提问把全部可见历史放进提示词。

优点是容易理解、便于短历史诊断；问题是每次都重复读旧材料，迟早超窗口。它适合做小样本参照，不适合作为无限增长历史的处理办法。项目的 full_history_control 是诊断组，不是上游摘要记忆基线。

### 方案 B：滚动摘要或会话摘要

操作：先让模型把对话写成“小林答应中午前给小陈送蓝色书”，以后优先读取摘要。滚动摘要会不断把新经历合入旧摘要；会话摘要则按会话保留多条。

摘要能缩短读取内容，但写摘要也要读原文、生成输出。连续改写可能把“12:00 UTC前”丢成“今天”，甚至把请求误写成接受。因此摘要必须保留来源，并单独测试否定、时间和承诺。

当前 baseline 适配的是会话摘要、评分和条件反思，不是一个无限更新的总摘要。

### 方案 C：原文归档 + 预算检索

操作：保留原文与向量，提问时取相关几条，直接交给模型理解。

它减少了写入时的生成式整理，对复查错误很直观；代价是逐消息向量和存储增长。检索遗漏、时间处理或相似句混淆仍会答错。当前三次开发重复实验的节省来自这一方案，但已发现迟到纠正失败。

### 方案 D：分层记忆

操作：保留原文，同时把不同信息整理到不同记录中。例如：

```text
原文层：保留小林说的原话和来源。
事实层：小陈喜欢蓝色书。（只有原文确实支持时才能写。）
承诺层：小林 -> 投递蓝色书 -> 小陈 -> 截止12:00 UTC -> 待完成。
回执层：执行器确认何时送到，用于更新完成状态。
```

好处是可以直接找未完成任务、当前事实或历史版本；困难是抽取可能出错、漏项或反复修复。尤其不能仅因上面两句对话就推断“小陈喜欢蓝色书”。JSON 格式合法也不代表语义正确。

本项目分层原型已经出现“回答输入更少，但整体 token 更多”，原因是抽取、维护和规划的新增工作超过了读取节省。

### 方案 E：原文 + 选择性结构化的混合方案

操作：所有可见经历保留原文；优先结构化明确承诺、身份和高复用事实；普通闲聊先归档，需要时检索。遇到冲突或缺失时有界回查原文。

这是根据当前项目现象提出的下一步候选方案，尚无完整实现和正式优胜结论。它的目标是控制“整理多少”而不是默认每句闲聊都值得调用模型抽取。

| 你的需求 | 本项目中可优先学习或验证的方案 | 要防止什么 |
| --- | --- | --- |
| 先弄懂链路、排查证据怎么进入模型 | 原文归档 + 预算检索 | 把相似度当事实判断；漏掉时间纠正 |
| 只测检索材料长度的影响 | 保持基线写入，单独改检索预算 | 把共享维护成本误算成零 |
| 需要按人物/关系/历史状态查询 | 版本化事实 + 原文来源 | 错误抽取和实体命名不一致 |
| 需要到期完成任务 | 明确任务状态 + 执行回执 + 预算保护 | 只靠向量检索临时想起承诺 |
| 想验证长期整体降耗 | 比较归档、分层和选择性混合方案 | 只看回答输入，忽略维护与失败 |

这里的“优先”指基于本项目的学习和实验顺序，不是推荐立刻替换当前架构。对当前研究，我倾向先把归档检索的证据链和时间语义做可靠，再加入有明确收益假设的结构化层。

## 4. “斯坦福小镇”与 Memory 是什么关系？

本项目使用 a16z AI Town 作为互动环境，不是斯坦福原版 Generative Agents 代码或论文的完整复现。

```mermaid
flowchart LR
    UI[地图与角色界面] --> W[世界引擎与事件]
    W --> O[角色实际观察]
    O --> P[记忆写入与存储]
    P --> R[检索与预算选择]
    R --> M[模型作出回答或动作决定]
    M --> X[执行器改变世界状态]
    X --> W
```

这张图解释目标工作循环；新离线策略接入在线循环仍未完成。界面负责看见角色，Convex 负责在线数据和引擎逻辑，Ollama 负责生成与向量推理，记忆策略决定模型读什么。它们互相配合，但不是同一个组件。

多个角色共用模型服务，就像多人共用一位顾问：每人带着自己的材料来咨询。可以共享模型权重，不能共享未授权的经历。

为什么先做离线实验？在线回答会改变接下来的轨迹：某组推理慢，可能更少交谈；某组忘记承诺，后续任务也会不同。固定对话与问题做离线比较，更容易知道成本差异来自什么；之后再进小镇检查长期行为反馈。

## 5. 用一笔具体的账理解 Token 成本

先记住三个账本：回答读写、记忆维护、Embedding。当前“总生成模型 token”包含前两者以及动作决策、规划和可获得的失败重试 usage；Embedding 单列。

下面全部是**假设的教学数值，不是本项目测量**，用于说明为什么压缩有时更贵：

| 每个阶段 | 原文检索 | 预先做摘要 |
| --- | ---: | ---: |
| 新会话写入的生成 token | 0 | 读原文600 + 写摘要100 = 700 |
| 每次问答的输入/输出 | 读900 + 写100 = 1000 | 读600 + 写100 = 700 |
| 只问一次的总生成 token | 1000 | 700 + 700 = 1400 |
| 问十次的总生成 token | 10000 | 700 + 10×700 = 7700 |

在这个人为简化的例子中，每次读取省 300 token，需超过两次查询才能抵消 700 token 的初始整理；问三次开始更少。实际系统还要加入更新、规划、重试和向量成本，且摘要必须保持质量。

这解释了两件事：写多读少时，提前抽取可能不划算；相同事实反复读取时，紧凑表示更可能回收成本。不能仅凭“摘要短”宣布成功。

云端费用还需分别乘输入、输出和向量模型实际单价，若有缓存收费也要分开；本文不提供供应商价格。当前本地 Ollama 没有按次云 API 账单，但有时间、内存、磁盘和电力成本。Token 降幅不等于费用、速度或耗电的同幅下降。

## 6. 4K 上下文够不够？应该怎么分配？

外部保存一万条历史不要求模型同时读取一万条。真正要检查的是：

```text
身份/规则 + 当前状态/问题 + 近期对话 + 检索记忆
+ 消息模板开销 + 输出预留 <= 实际模型窗口
```

以下仅为 4096-token 窗口的**教学分配**，不是当前已运行配置：

| 项目 | 假设预算 |
| --- | ---: |
| 身份与规则 | 500 |
| 当前状态和问题 | 400 |
| 近期对话 | 700 |
| 检索记忆 | 1200 |
| 模板等开销 | 200 |
| 输出预留 | 512 |
| 合计 | 3512，剩余584作为余量 |

实际长度必须用模型对应 tokenizer 计算，并与服务 usage 校准，不能把中文字数直接当 token。遇到超限时先看是哪部分占用；只减记忆可能会丢掉完成任务必需的证据。

项目以 8K 作为主要对照、4K 作为压力测试。窗口变大给了更多材料空间，却不会自动修复漏检、错误摘要和事实时间问题。

## 7. 当前实验数据怎样读？

[固定三次重复报告](../experiments/policy-comparison-2026-10-16T14-46-33-809Z-2b92c0de-summary.json)使用相同的 10 道开发题，三次独立重建，归档组预算为 512 token，窗口为 8K。

| 指标，三次合计 | 基线 | 归档检索 |
| --- | ---: | ---: |
| 问答正确 | 27/30 | 30/30 |
| 单步合成投递完成 | 3/3 | 3/3 |
| 回答输入 token | 13374 | 8544 |
| 回答输出 token | 222 | 222 |
| 全部生成输入 + 输出 token | 23184 | 9957 |
| Embedding 调用数 | 51 | 69 |
| Embedding 输入 token | 2376 | 2214 |
| 保存的 JSON 快照字节 | 495045 | 976731 |

“回答输入减少36.11%”是少读材料；“总生成 token 减少57.05%”还包括少做生成式维护；“快照1.97倍”是外部保存文件约增加97%。它们可以同时发生，就像桌面纸张少了、秘书整理工作少了，但档案柜变大了。

快照是三次策略 JSON 文件的合计，包含原文、向量和元数据，不是 RAM 或整个数据库。基线也保留独立原始实验资料。Embedding 调用更多说明另一个成本仍在增加。

这只是十道题的重复，不是三十道独立题；也不是连续在线任务验收。分层方案另一轮单次对照曾出现回答输入下降约8.75%，总生成 token 却增加约63.11%，见[验收记录](ACCEPTANCE.md)。这些证据用于理解取舍，尚未证明哪种方案普遍最好。

## 8. 亲手操作：先读结果，再跑一次对照

所有命令在项目根目录执行。下面是供你学习时操作的步骤，本次文档修改没有启动服务或运行模型。现有模型和依赖已准备好的情况下，不需要重新下载、初始化小镇或清空数据库。

### 8.1 不启动模型，先理解现有结果

```bash
npm run check
cat configs/archive-quality.repeated.development.json
cat experiments/archive-research-summary.json
```

第一条只检查项目文件和配置结构；`UNSET` 提示表示正式草案仍有信息待补齐，不等于上述开发配置完全不能运行。第二条重点找 `variants`、`contextWindowTokens`、`memoryBudgetTokens` 和 `repetitions`：它们分别说明比较谁、窗口多大、给记忆多少空间、重复几次。

第三条会看到正面开发 run、负面边界 run，以及 `formalQualityAccepted: false`。它表示正式质量尚未验收，不能只摘录节省率而略过失败。

### 8.2 准备 Ollama 和计量网关

终端 A 先检查：

```bash
curl -fsS http://127.0.0.1:11434/api/version
ollama list
```

如果模型列表缺少 `town-qwen` 或 `mxbai-embed-large`，按[本地部署](LOCAL_SETUP.md)准备，先不要运行对照。不要覆盖现有别名；开发配置还会核验模型摘要等条件。

### 8.3 跑固定的归档对照

终端 C：

```bash
npm run policy:compare -- --config configs/archive-quality.repeated.development.json
```

程序会打印“记录目录”，然后独立维护两组记忆、恢复检查、回答问题并执行单步合成投递。保存打印的实际目录。失败时保留该目录，先看错误，不无限重跑。

接下来先定义变量，把字符串替换为刚打印的目录；此处是占位说明，不能原样照抄路径：

```bash
townRunDirectory='替换为刚打印的实际run目录'
npm run memory:compare:evaluate -- "$townRunDirectory" experiments/datasets/memory-quality.development.answers.json
```

评分器在模型运行结束后读取独立答案。它会打印 `artifact`，值类似 `evaluation-某个哈希.json`。将这个实际文件名填到下面，不要填完整路径：

```bash
townEvaluationFile='替换为artifact输出的实际文件名'
node scripts/report-memory-comparison.js "$townRunDirectory" "$townEvaluationFile" --no-latest
```

`--no-latest` 会生成这个 run 的报告而不替换主结果入口。它仍会写当前 run 的派生报告；旧内容发生变化时按哈希保留修订。不要把不同 run 的评分文件混在一起。

## 9. 遇到问题时，按什么顺序找原因？

### 9.1 模型答错：先查证据，再怀疑模型

```text
原始可见消息里有证据吗？
  没有 -> 应回答未知，检查是否真的有观察资格。
  有 -> 快照中保存正确吗？
         不正确 -> 写入、摘要或抽取问题。
         正确 -> 检索候选/选中列表里有吗？
                  没有 -> 查时间过滤、相似度和预算排除。
                  有 -> 核对实际输入/模板和输出状态，再做最小证据诊断。
```

如果直接提供最小正确证据仍答错，才更有理由检查模型理解、提示词和输出上限。这个定向诊断不能混入正常检索成绩，因为它人为提供了正确证据。

### 9.2 真实遇到的时间问题：后来纠正了过去

```text
11月1日：听说图书馆9点开门。
11月2日：收到纠正，11月1日实际8点开门。
```

问“11月1日当时我认为几点开门”，回答9点合理；问“根据现在的信息，11月1日实际几点开门”，应回答8点。

当前归档策略可能看到问题日期就排除之后的消息，因此把纠正也排除了。在[独立边界测试](../experiments/policy-comparison-2026-10-16T14-51-34-915Z-015fd670-summary.json)里，基线2/2，归档1/2。

拟解决方式是分开保存/查询“何时获知”和“事实何时有效”，并保留纠正或撤回关系；这还未完整实现。不能直接去掉所有时间限制，否则角色会使用当时不知道的信息。

### 9.3 常见现象与下一步

| 现象 | 容易产生的误解 | 实际应检查什么 |
| --- | --- | --- |
| 上下文超限 | 一定要换大模型 | 身份、近期对话、记忆、模板、输出预留分别多大；是否整条跳过并记录 |
| 存了很多但记不起来 | 数据库丢了 | 作用域、候选排序、时间过滤、预算和选中来源 |
| 输入少了，整体更贵 | 计量错了 | 抽取、规划、评分、反思、修复和重试是否增加 |
| JSON 合法但事实不对 | Schema 已保证正确 | 原文是否支持主语、属性、值和时间；是否漏掉否定 |
| 承诺题答对但没履行 | 模型已经完成任务 | 是否真的接受、是否有库存/接收人、执行器是否留下回执 |
| 重启后重复记忆或多次生成 | 只做去重就够 | 幂等键是否含作用域；区分已提交事务与未完成维护；重复计算也要计量 |
| 模型超时 | 再无限重试 | 检查网关、排队、模型重载和内存压力；按上限停止并保留 attempt |
| 向量维度/版本错误 | 清空数据库重建 | 模型摘要、维度与索引版本；新模型应独立建索引，保留旧实验 |
| 在线组 token 更少 | 新策略更省 | 是否只是更少交谈、任务更少或提前停止；比较活动量和轨迹 |

## 10. 如果由我继续搭建，会按什么顺序？

这是学习与研究建议，不是已经实施的新架构决策：

1. **先把“原文 + 检索 + 预算 + 来源”学透。**能从一次回答追到原文、候选和花费，才方便判断后续组件是否有用。
2. **修复时间查询合同。**同时测试“当时知道什么”和“现在回看过去”，加入纠正、撤回与否定案例。
3. **加入小而明确的任务状态层。**明确接受、截止、取消和回执，关键任务预算不足时显式处理，不依赖偶然检索。
4. **只对有收益假设的信息做结构化。**比如频繁查询的稳定事实；比较不同加工频率，把抽取失败与维护 token 全部入账。
5. **用独立题集和长历史比较。**先保持模型、输入和工作量固定，再进入真实小镇；最后测4K、长时故障恢复和干净环境复现。

当前状态：P0规范已完成，P2小镇工程验收通过；P1人工核验与P3部分上游等价验证待补齐，P4正式质量矩阵未完成，P5长时在线和P6完整复现尚未完成。研究门槛是质量与工作量可接受时再谈成本收益，不能把开发样本的好成绩当作通用结论。

## 12. 从情景聊天的“世界书”理解上下文管理

### 12.1 网站实际披露了什么？

2026-10-18 查阅用户指定的 yeyu.pro，只研究记忆与一致性。其[世界书教程](https://www.yeyu.pro/4)称：角色核心设定常驻，背景条目按关键词注入；条目有优先级与匹配条件，支持递归触发及动态派生。[创作指南](https://www.yeyu.pro/1)给出通过作品编辑页添加关键词、内容及触发配置的操作说明。

这是网站公开教程的功能描述，不是对后端代码或实际请求的验证。未登录、未发送对话，也未测量其 token。实际主站已打开，但本次未取得可核验的记忆设置。自动摘要周期、向量数据库、具体裁剪顺序、冲突处理及动态派生算法均无法确认；“支持动态派生”也不能证明采用了 LLM 抽取。

下面是我们从这些说明得到的设计分析，不能当作该网站已实现的架构。

### 12.2 世界书与聊天记忆的区别

可以把世界书看成剧组的设定卡，聊天记忆看成已经拍摄的剧情记录。

```text
设定卡：小林是图书管理员，说话简短；图书馆位于广场东侧。
剧情记录：今天小林答应给小陈送蓝色书。
当前状态：书已交付，小林现在位于咖啡馆。
```

设定卡负责“这个人是谁、这个世界有哪些规则”；剧情记录负责“过去发生过什么”；当前状态负责“现在事情进展到哪一步”。如果只反复插入设定卡，角色可能一直像小林说话，却仍然忘记已经送过书。

这让我们可以把一致性拆成三个可测试目标：人设是否稳定、经历是否记对、当前状态是否正确。它们应由不同来源支持，不能只用一个问答准确率代表全部能力。

### 12.3 用“去图书馆还书”演示一次上下文组装

以下为小镇的候选设计，尚未接入现有 runner：

用户说：“我们去枫叶图书馆还书，之后找小陈。”

1. **常驻核心**：放入简短身份和说话风格，不放完整人物传记。
2. **程序状态**：读取该角色可见的位置、库存和待办。如果蓝色书已经送出，模型不能凭历史承诺再生成一次投递。
3. **触发设定**：关键词“枫叶图书馆”命中地点条目，“小陈”命中允许该角色访问的人物条目。
4. **检索经历**：从原文归档中找与还书、小陈及未完成事项有关的消息；处理明确提及和代词指代的区别。
5. **核对与去重**：同一来源不因被关键词和向量同时找到就重复注入；冲突事实保留时间与来源，不按相似度决定真伪。
6. **分配预算**：关键状态和身份先预留空间，再装入近期对话、触发条目和相关经历；记录被排除的条目及原因。

模型收到的就像一份本场戏的资料包：角色名牌、当前场景单、相关设定卡、几段过去剧情。它不必读取全镇百科，也不应看到其他角色的私密剧情。

### 12.4 对小镇有帮助的候选架构

```text
简短常驻身份 ─────────────┐
当前可见状态与待履行任务 ──┤
近期原始对话 ─────────────┤
关键词/地点/人物触发的设定 ─┼→ 权限与时间检查 → 去重/冲突处理 → 预算组装 → 模型
向量检索到的过去经历 ──────┘
```

其中，关键词路由是“明确提到某实体，就查对应资料”；向量检索是“根据问题含义，找可能相关的经历”。两者可以互补。比如“枫叶图书馆”适合明确匹配；“上次借书的地方”可能需要近期对话中的指代解析或语义检索。

| 材料 | 候选存放方式 | 何时读入 | 主要成本 |
| --- | --- | --- | --- |
| 核心身份/风格 | 短角色卡 | 每轮 | 每轮固定输入 |
| 地点与稳定背景 | 带作用域、版本的设定条目 | 实体或场景触发 | 被选中后的输入；人工维护也需记录 |
| 当前位置、库存、任务 | 执行器或任务状态记录 | 相关决策前 | 状态渲染输入；现有权威状态通常不必再用模型抽取 |
| 近期对话 | 有界原文窗口 | 每轮 | 输入随窗口长度变化 |
| 历史经历 | 原文归档与向量 | 相关查询时 | 写入/查询 embedding、检索时间和选中原文输入 |
| 长期总结 | 有来源的派生记录 | 达到明确维护条件时 | 总结生成与后续更新，需要证明能回收成本 |

这些是逻辑层，不要求部署六个数据库。当前项目已有多项基础，但设定条目触发器、统一组装器以及完整混合回查尚未实现。本节提供候选思路，不改变已批准的实验基线。

### 12.5 为什么可能节省 Token，又为什么可能失效？

下面只是教学算例：假设背景资料总长 3000 token，一轮只需两条、共 300 token。与每轮完整注入相比，这部分输入少 2700 token；若每轮再用模型花 400 token 决定选哪些条目，净节省就需扣掉这笔规划成本。

简单关键词匹配可以由普通代码执行，本身不需要生成调用，但匹配、存储和维护仍有计算/人工成本；被注入的文字依然占输入 token。若角色卡和世界书写得过长，固定开销会挤掉真正相关的对话记忆。

递归触发尤其需要限制。假设“图书馆”触发“管理员”，管理员条目又提到“咖啡馆”，再触发“街区”，一次还书问题就可能带入半个小镇。我们可先测试不递归或只扩展一层，并设置访问过的条目集合、最大条数和总 token 上限，记录触发链。具体上限应进入实验配置，不能默认为越多越好。

### 12.6 需要防止的四种一致性问题

| 问题 | 生动例子 | 候选处理方式 |
| --- | --- | --- |
| 没有关键词就失忆 | 刚说过图书馆，下一句“那里几点关门”却没有命中 | 保留近期对话，明确实体别名，测试语义回退；计入额外成本 |
| 旧设定压过新事实 | 设定卡写9点开门，但今天收到8点开门的纠正 | 背景规则与时效事实分开；用知识截止时间和事实有效时间解析 |
| 未完成与已完成混在一起 | 历史里仍有“要送书”，实际上昨天已送到 | 当前任务状态关联执行回执；模型说完成不能单独改变状态 |
| 触发词让角色知道秘密 | 提到某人名字，就读到对方私密经历 | 触发前检查观察资格与访问范围；全镇事件日志不直接作为角色记忆 |

对第二项尤其要谨慎：新消息也可能只是传闻，不能机械地“最新消息覆盖一切”。应记录谁说的、何时知道、适用何时，以及是否存在明确纠正关系；证据不足时保留冲突或未知。

### 12.7 怎样验证这项启发是否真的适合我们？

下一步可以先做只读上下文组装探针，不急于重写全部记忆层：保持模型、原文历史、角色权限与任务一致，比较三种组装方式——允许访问的全部设定、关键词触发设定、关键词加语义回退。另设相同 token 预算的比较，避免把“给得更多”当成检索更好。

题目至少覆盖：明确地点名、别名、连续代词、话题切换、递归循环、角色秘密、迟到纠正，以及已经完成的承诺。除总输入和维护成本外，记录设定误触发、相关证据漏选、人设漂移、事实矛盾及任务完成。

触发规则只能依据角色可见输入和预先配置的设定，不能为命中测试答案而定制。需要新增世界书数据时，应冻结共同的初始设定并提供来源，不能只给优化组额外知识。待明确合同后再记录正式架构决策并实施。
